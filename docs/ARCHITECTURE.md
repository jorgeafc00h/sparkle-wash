# Current architecture

The active workflow is arrival → staff confirmation → detailing job. An ESP32 camera can submit a keyed, bounded observation containing a device event ID, plate candidate, confidence, capture time, and optional JPEG. `ArrivalStore` persists observations and deduplicates retries. A candidate does not become a job until an authorized staff member confirms the plate and vehicle class.

`PackageCatalog` loads `contracts/v1/service-packages.json`, including the supplied four packages and four vehicle-class price columns. `JobStore` snapshots the chosen package, services, and price when the job opens; it records transitions and assignments and computes elapsed time and whole-carwash counts on the server. `OperationsStore` holds employees, inventory items, append-only stock movements, and job reservations. JSON replacement writes are atomic within each store, while transactions across stores are not yet provided. This storage layer is suitable for a prototype, not a multi-node deployment.

The API runs in `backend/src/carwash-api/Program.cs` on ASP.NET Core (.NET 10). `Program.BuildApp` is the same application used by HTTP integration tests. Staff access uses a verified Google ID token exchanged for a short-lived session, with viewer/operator/admin role checks. The web sign-in uses Google Identity Services; the iOS app uses GoogleSignIn. Each requires project credentials and the server staff allowlist. Camera ingest uses a separate device key. N1CO webhook signatures are checked and retained, but checkout, job reconciliation, and receipts remain pending.

The mounted web app is `frontend/src/OperationsApp.tsx`. It shows the package menu publicly and refreshes arrivals, jobs, whole-carwash totals, employees, and stock after staff sign-in. Operators can confirm an arrival, open a job, transition it, and assign an employee. The active SwiftUI root is `OperationsView.swift`, built from `project.yml`; it provides the corresponding read and core job actions and keeps an endpoint-scoped SwiftData read cache. Both clients still need full stock editing, payment, evidence, streaming, and accessibility acceptance.

Legacy station routes remain for compatibility. `StationStore` persists latest station readings and wash records. `MqttBridge` and `StationHub` carry authenticated station telemetry. Until a station submits telemetry, `/api/metrics` and `/api/metrics/alerts` return labeled demo samples; the legacy `/api/upload` only acknowledges requests. Neither is a job count. Other web screens and `frontend/src/api.js` are experiments and are not mounted. ESP32 firmware and deployment templates remain unverified against the new arrival contract.

See `contracts/README.md` for DTO decisions, `docs/openapi.yaml` for HTTP routes, `openspec/specs/` for implemented behavior, and `openspec/changes/complete-platform-parity/` for remaining work. Historical architecture is preserved in `docs/archive/2026-10-18/`.
