# SparkleWash iOS review and implementation plan

Reviewed November 5, 2026 against the active iOS 18 target, API archive routes, current OpenSpec, simulator tests and Apple documentation. The Xcode project is generated from `SparkleWash-iOS/project.yml`.

## Current implementation

- The active app is a SwiftUI operations workboard with a restrained teal accent, SF Symbols, semantic surfaces, adaptive SwiftUI text styles, and textual job-state labels. The November 4 iPhone 17 Pro dark-mode capture verifies the public catalog only; it does not verify signed-in screens or the latest contrast changes.
- Arrivals and jobs are `Section` containers in one `LazyVStack` with `pinnedViews: [.sectionHeaders]`. The status strip sits in a top safe-area inset. This structure is used across widths, though signed-in iPad and landscape behavior still needs visual validation.
- Job cards use an iOS 18 matched zoom navigation transition. Reduce Motion selects standard navigation and disables the job movement and status animations. State changes animate; routine polling does not intentionally animate.
- Secondary copy now uses `Color.primary.opacity(0.72)` on semantic system surfaces to improve adaptive contrast. No post-edit light/dark contrast measurement has been recorded. Reorder warnings and other semantic status colors also need measured contrast and VoiceOver review.
- SwiftData stores endpoint-scoped operational snapshots and one `CachedArchivedJob` row per history job, scoped by endpoint plus tenant, subject and role. The archive cache has a 24-hour maximum. Restore scrubs expired operational data and validates saved history; sign-out deletes the endpoint's operational and archive rows.
- Expiry cleanup now removes archived rows by each row's own sync timestamp. A regression test confirms expiration of one endpoint snapshot does not delete a still-valid row for a different staff scope at that endpoint.
- Archive downloads now persist the index cursor, batch and offset alongside each committed job page. The app resumes a timed-out page, keeps staged rows inaccessible until the signed revision completes, and clears the scoped cache when a batch is withdrawn or the archive revision changes. The previous 100-batch and 1,000-job client caps are removed. A changed revision currently triggers full cache invalidation and rebuild rather than selective tombstone application.
- Cold-launch history access is implemented with a server-issued ES256 grant, bound to API origin, tenant, staff subject, role and archive revision, with a maximum 24-hour lifetime. The app verifies the grant and uses it only for read-only saved history; it does not restore a bearer token or enable staff mutations. History expiry is checked while the history view is open and when returning to the foreground.
- The API requires `SPARKLEWASH_OFFLINE_SIGNING_PRIVATE_KEY` to issue grants. A dedicated P-256 key is now stored as a protected GitHub `ibm-demo` environment secret, and the matching Code Engine secret-name variable is set. The key has not been synced to Code Engine or used by a deployed API. On first authenticated sync, the app verifies the grant over HTTPS and pins its P-256 public key in the device-only Keychain, scoped to API origin. Cold-launch verification requires an exact match with that pin; a later signed-in HTTPS sync can rotate it. Simulator tests reject a self-signed replacement and exercise rotation through an injected key-store implementation. Device Keychain behavior across app reinstalls and key rotation still needs acceptance testing.
- The archive API reads compressed tenant files under `SPARKLEWASH_ARCHIVE_DIR` in the JSON profile. With `SPARKLEWASH_POSTGRES_WORKFLOW=true`, it reads completed jobs directly from PostgreSQL using tenant-scoped revision tokens and bounded pages. Migration `003_archive_revisions.sql` and its runtime SELECT grant were applied to Neon `main` via Neon CLI on November 5, 2026; the grant was verified to allow SELECT but not UPDATE. PostgreSQL 18 integration tests cover revision changes, cross-tenant denial, tenant moves, and the authorized HTTP route. The workflow flag remains off in the cloud, and Neon-to-IBM COS export is not connected to the API reader. SwiftData remains a 24-hour device cache, not the durable archive of record.

## Remaining findings

1. **Cold-offline entitlement: implementation present, production validation incomplete.** The simulator test creates a new `OperationsModel` over a reopened disk-backed store and verifies saved history without sign-in. It also checks signature tampering, replacement-key rejection, origin/staff-scope mismatch, expiry, tenant switch, sign-out, batch withdrawal, key rotation, and preservation when the Keychain adapter is temporarily unavailable. This verifies model-level cold restoration, not a full app termination/relaunch, real Keychain persistence, or revocation against a deployed server. Add expiry-deletion and on-device Keychain acceptance; verify the protected signing secret is installed before enabling the archive endpoint in a cloud environment. The 24-hour grant is the maximum revocation delay while a device remains offline.
2. **Large-history sync now resumes bounded pages; deletion reconciliation remains conservative.** The client persists the index cursor and page offset in SwiftData and commits each page with its checkpoint. A simulator test interrupts page two, reopens the disk-backed store, verifies partial rows remain inaccessible, and confirms retry resumes from the saved offset. The PostgreSQL endpoint rejects a stale batch revision, which makes the client rebuild the full scoped snapshot; selective tombstones remain open under OpenSpec 6.5/6.6. There is still no aggregate row/byte quota for the local store.
3. **Neon export and long-term retention remain separate from the online page reader.** The API can page completed jobs from Neon after migration 003 and its runtime grant are installed, but COS export, API reads from COS, isolated COS restore evidence, and hold-aware purge are not complete. Keep automatic purge disabled until an independent server archive and restore path is proven. SwiftData must remain a bounded local read cache, not the only surviving copy of records purged from Neon.
4. **Local data protection and storage bounds remain open.** The app has time-based eviction, but there is no explicit verified policy for SwiftData file protection, device backup exclusion, maximum cache rows/bytes, or cleanup after database/backup restore. Define these before storing plates long term. The grant and cached rows are local data and need the same protection policy.
5. **Visual/accessibility acceptance remains partial.** Arrival and job navigation labels now announce the camera, candidate confidence, review state, package, price, elapsed time, and assigned staff that the visible cards show. The public catalog has a default-size dark-mode smoke capture. Signed-in screenshots/interactions are still needed on iPhone and iPad in portrait and landscape, with large Dynamic Type, VoiceOver focus around pinned headers, light/dark mode, Reduce Motion, and navigation return position. Configurable haptics in the parity spec are not implemented in active SwiftUI code.

## Implementation order

1. Complete signed-entitlement security/expiry acceptance: verify a true app cold relaunch, Keychain pin persistence, history removal at expiry, key rotation, and behavior after sign-out, tenant/account switch, offline expiry and confirmed revocation. Keep signing keys in the protected server runtime only.
2. Keep PostgreSQL feature flags off until directory/device/workflow/inventory cutover, import rehearsal, and restore pass. Then test the live tenant-scoped page route against Neon. Connect verified COS batches to the API reader with manifests, counts and checksums; restore into an isolated database before considering any purge. Keep the proposed 90-day online job and 30-day online evidence windows as planning assumptions pending policy approval; IBM Archive objects have a 90-day minimum retention before deletion.
3. Add API deletion/revocation markers and selective tombstone application. The client now resumes bounded page downloads without a full-history buffer or fixed record cap; preserve its fail-closed behavior and test cursor invalidation when server revisions change.
4. Set the local SwiftData protection, backup and size policies; implement and test backup/restore cleanup and expiry deletion. Do not cache photo bytes in this archive; keep verified evidence references only.
5. Complete signed-in visual/accessibility acceptance on phone and tablet, then implement configurable haptics. Keep a coherent native operations visual language: semantic system surfaces and color, consistent card and status-chip shapes, clear empty/loading/error states, and adaptive grid/gutters rather than device-specific fixed widths. Keep each action at least 44 pt, make status meaning available in text and VoiceOver, and avoid content hidden under the pinned status strip or section headings. Fix any clipping, insufficient contrast, focus obstruction, or scroll restoration issues found. Capture evidence for both themes and Reduce Motion.
6. Re-run `make ios-build` and `make ios-test`; keep OpenSpec task 6.6 open until cursor resume, tombstones, entitlement expiry/revocation, tenant switching and cold restore meet its full acceptance criteria.

## Apple platform references

Apple's current guidance supports grouping content in `Section` inside a lazy stack and pinning headers with `pinnedViews`. WWDC26 explains lazy-stack size estimation, prefetching and scroll-position implications: keep important state outside lazy child views, avoid layout changes after appearance, and preserve a semantic visible item when the dataset or orientation changes. Do not derive restoration from raw content offsets; use `ScrollPosition` and stable item IDs if implementation needs explicit scroll restoration. Scroll-transition effects must not transform off-screen rows into the visible rect. These details support a restrained finish: animate only meaningful state changes and navigation, never the periodic refresh itself, and use fades or no transition under Reduce Motion.

The current visual implementation is a sound native baseline, not yet signed-in-screen acceptance: the verified captures cover only the public catalog. Before calling the app polished, capture the active workboard and job/arrival flows at small and large phone sizes and iPad portrait/landscape, in both appearances and large Dynamic Type. Check that pinned headings and the top status inset do not cover VoiceOver focus; verify status meaning without color, loading/error/empty states, 44 pt actions, and return-to-list position after navigation. Apple HIG motion guidance recommends purposeful, brief, interruptible feedback and a reduced-motion alternative; the existing `.snappy` state update and zoom navigation should be checked against those cases rather than adding decorative continuous effects.

`ModelContext` manages model lifecycle and persistence; explicit saves are appropriate where the app replaces a downloaded archive snapshot. The current SwiftData archive is an endpoint/staff-scoped cache that expires after 24 hours. Define and test store protection, backup exclusion, size bounds, and restore cleanup before retaining plate data longer. The database cache is not a substitute for a durable Neon-backed archive and independently restored object copy.
