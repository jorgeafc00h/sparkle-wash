# SparkleWash Desktop (Electron + Vite + React 19)

Custom build of the Facturas Simples desktop app (1.4.6 copy; the original is read-only upstream) plus the carwash
workflow. Full contract: [docs/SPARKLEWASH_INTEGRATION.md](docs/SPARKLEWASH_INTEGRATION.md). Install/run/build: [README.md](README.md).

**Layout** (`backend/desktop`): `electron/` (main, preload, builder config, `carwashProxy.cjs`), `src/`, `public/` (icons),
`docs/` (`upstream/` = inherited MH-auth reviews and old README), `scripts/` (`verify-packaged-app.cjs`, `make-ico.cjs`).
Carwash modules: `src/services/carwash/*` (types, `CarwashApiClient`, `CarwashSettingsStore`, `CarwashOutbox`,
`CarwashSyncService`, `workTicketNumber`), `src/store/slices/carwashSlice.ts`, `electron/carwashProxy.cjs`,
`src/services/printing/WorkTicketPrinting.ts`, `src/pages/carwash/*`, `src/components/carwash/*`,
`src/pages/pos/PosRegisterPage.tsx` ("Cobrar lavado").

**Verify** (from `backend/desktop`): `npx tsc --noEmit`, `npx jest`, `npx vite build`; packaging check:
`CSC_IDENTITY_AUTO_DISCOVERY=false npx electron-builder --config electron/builder.config.json --dir -c.mac.notarize=false`
then `node scripts/verify-packaged-app.cjs <app.asar>`. CI: the `desktop` job in `backend/.github/workflows/ci.yml`.
Web Playwright: `npx playwright test` (490 specs). `playwright/tests/carwash/` starts the real carwash API through
`../src/carwash-api.DevHost` (needs the .NET 10 SDK). The Device Sync relay specs (`pro/11`, `13`, `15`, `16`) build the
upstream relay: set `SYNC_API_PROJECT_DIR="/Users/jorgeflores/github/FACTURAS SIMPLES/Invoices.Api/Invoices.SyncApi"`
(the fixture's default sibling path does not exist inside this repo).

**Rules**
- Data isolation: `main.cjs` calls `app.setName('SparkleWash')` and pins `userData` to `<appData>/SparkleWash` before any
  `getPath('userData')`. Secure-storage service names are `SparkleWash*`; never read Facturas Simples paths, keychain items
  or storage. Google Drive folder/backup prefix are `SparkleWash`.
- Updates are opt-in: never add the Facturas Simples blob (`sticongen.blob.core.windows.net/installer`). Only start
  electron-updater when `SPARKLEWASH_UPDATE_URL` or a baked `publish` config (`app-update.yml`) exists.
- Keep "Facturas Simples" only where it names the upstream invoicing service/backend, plan names, legal DTE text, and
  the PDF free-tier footer. App-facing names are "SparkleWash". UI text in Spanish.
- Keep `electron/builder.config.json` `files` listing `electron/*.cjs` and runtime deps in `dependencies`.
- Do not change API hosts, OAuth client ids, telemetry keys or the sync relay config without an explicit task.
- `.github/workflows` inside `desktop/` does not run; CI lives in the repo root workflow.

## Key Architecture

### Electron IPC Bridge
All Electron APIs are exposed via `preload.cjs` → `window.electronAPI`:
- `googleSignIn(clientId, clientSecret)` — OAuth loopback flow (localhost:9876)
- `secureGet/Set/Delete` — OS keychain via safeStorage
- `sha512(text)` — Node crypto (avoids crypto.subtle issues on Windows)
- `storage.*` — persistent key-value store (replaces localStorage for app:// protocol)
- `printToPDF` — PDF generation via hidden BrowserWindow
- `showSaveDialog/showOpenDialog` — native file dialogs

### Certificate Flow (MH .crt XML)
1. User uploads `.crt` file → `CertificateService.storeCertificateForCompany(nit, xml, sha512hash)`
2. Password stored as **SHA-512 hash** (matches `privateKey.clave` in the XML)
3. `SignerService` caches parsed cert in memory for JWS signing
4. `validateCertificate()` compares stored hash against XML `clave` field

### DTE Submission Flow
1. `DTEMappingService` builds the JSON body for the DTE type
2. `SignerService` signs the JSON body (PKCS#8 RSA + JWS)
3. `InvoiceService.syncInvoice()` → `POST /document/send` to Invoices.Api
4. API authenticates with MH (`POST /seguridad/auth` → Bearer token)
5. API forwards signed DTE to MH (`POST /fesv/recepciondte`)
6. Response: sello de recepción + estado (Completada/Rechazada)

### Google OAuth (Electron) — `electron/googleOAuthService.cjs`
- Consent opens in the user's **system browser** (`shell.openExternal`; Google disallows OAuth in embedded webviews) — the renderer shows `GoogleSignInPendingDialog` (Cancelar / Abrir de nuevo) meanwhile
- One-shot loopback listener on `127.0.0.1` with a **random port** (`/auth/callback`; Desktop-type clients accept any loopback port); foreign-`state` callbacks are ignored; 5-min timeout
- Code exchange sends **PKCE AND `client_secret`** — Google's token endpoint rejects a Desktop client's exchange without it (`client_secret is missing`). The renderer passes `VITE_GOOGLE_CLIENT_ID/SECRET` over IPC (packaged main has no `.env`); dev main falls back to `process.env` (dotenv `.env`/`.env.local`)
- id_token claims checked (iss/aud/exp/nonce); refresh tokens stay in main (`secrets.json`, safeStorage) keyed `google-oauth::refresh:<sub>`, one entry per scope set — `auth:google-refresh` renews, `auth:google-signout {revoke}` revokes on explicit logout
- Scopes: sign-in asks `openid email profile` only; `drive.file` / `gmail.readonly` are requested on first use via `GoogleAuthService.getAccessTokenForScope(scope, { interactive })` (cached → refresh → consent; granted scopes checked — granular consent). Compras Gmail links store `googleAccountId` + `tokenExpiresAt` and renew through `services/compras/GmailAuthService.ts`

## Build & Deploy

### Development
```bash
npm run dev          # Vite dev server (web)
npm run electron:dev # Electron + Vite (desktop)
```

### Windows installer
```bash
npm run build:electron -- --win   # tsc + vite build + electron-builder NSIS + zip
# Output: electron-dist/FacturasSimples-Setup-{version}.exe
```

### macOS installer
```bash
npm run build:electron -- --mac   # universal DMG + zip (zip is required for auto-update)
# Output: electron-dist/Facturas Simples-{version}-universal.dmg
```

CI (`.github/workflows/build-windows.yml` / `build-macos.yml`) uploads versioned artifacts + `latest.yml`/`latest-mac.yml` + stable-name aliases to the `installer` Azure blob container on every push to main. Bump `version` in `package.json` (or use the workflow's `version` input) for each release — the auto-updater ignores builds with the same version, and the landing page links only the stable aliases.

## Subscription Tiers

Configured in `src/config/subscriptionConfig.ts`:
- **Lite** (free): all DTE types, local signing, 1 company, 10 invoices/month (production companies only), rewarded ad before sync, app logo on PDFs
- **AdFree** = "Pro" ($7): 2 companies (landing FAQ/Documentation say "hasta 2 empresas"; `FeatureGate.maxCompaniesForTier` returns 2 — the old "3" here was stale), no ads, JSON/batch-PDF export, Drive upload, email
- **Pro** = "Business" ($14): unlimited companies, cloud sync, batch PDF, Google Drive backup, Libros IVA

Gates enforced in the UI (`FeatureGate.ts`): company-count limit on `CreateCompanyPage`, paid format gates on `InvoiceExportPage` (Excel stays free), Drive/Libros IVA/Azure-sync gates on their pages. `N1COService.normalizeTier` maps the backend's Pascal-cased tiers onto the lowercase enum — apply it to any new endpoint that returns a tier.
